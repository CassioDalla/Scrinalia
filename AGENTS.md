# AGENTS.md

## About the project
A system for archivists to catalog and manage archival descriptions (ISAD(G) metadata), with AI enrichment (NER, zero-shot classification, clustering) and Human-in-the-Loop governance.

Three-layer pipeline, each layer a domain under `src/scrinalia/domains/`:
`ingestion` (scraping queue) -> `staging` (structured, cleaned data) -> `archive` (final enriched document + human review).
A fourth domain, `identity`, is not a layer of that pipeline: it owns the accounts, the sessions and
the role map (ADR 0009).

- Layout: `src/scrinalia/` is the installed namespace (`api/`, `core/`,
  `domains/`). `main.py` at the root only re-exports `scrinalia.asgi.app` so
  `uvicorn main:app` keeps working; put application code in the package, never in `main.py`.
  `testing/`, `migrations/` and `docs/` live **outside** the package on purpose. There is no
  `scripts/`: one-off tooling is deleted once it has served its purpose instead of being kept
  at the root, where it rots with stale imports.
  See `docs/adr/0002-src-layout-and-internal-namespace.md`.
- API: Litestar, assembled in `src/scrinalia/asgi.py` (`create_app()`), NOT FastAPI.
  Decision recorded in `docs/adr/0001-litestar-as-http-framework.md`.
- Front: the curator UI is the React SPA in `apps/curator/` (ADR 0003). It is the only front end:
  the temporary Streamlit dashboard was removed in B8. Treat the API as the stable interface.
- Code is written in **English**: filenames, identifiers, comments, docstrings, log messages and internal error messages. Only end-user-visible text stays Portuguese (see Language below). Commits follow Conventional Commits.
- `README.md` is the front door for newcomers (what the system is, how to run it); the roadmap
  lives in `TODO.md` and the accepted architecture decisions in `docs/adr/`. Keep all three in
  step with the code, and never state something in them that you have not verified.
- **License: `AGPL-3.0-only` plus one additional term** under section 7(b) requiring the author
  attribution to be preserved (`LICENSE`, `LICENSE-ADDITIONAL-TERMS.md`, ADR 0006). Two rules:
  never inline the attribution text in a component — it is defined once in
  `apps/curator/src/lib/attribution.ts` and rendered by `AttributionFooter` through `AppShell`, so
  every screen shows it and a rename touches one line; and never add a term beyond attribution,
  because the license declares any other non-permissive additional term to be a "further
  restriction" that section 10 forbids imposing. "Modifications must be contributed back" is a
  request in the `README`, not a condition — no license can require it.

## Commands
Always run from the repo root. Python 3.12 managed by `uv` (`uv.lock`).

- Install deps: `uv sync` (heavy: `torch`, `transformers`, `spacy`, `bertopic`).
- Whole dev stack in one command: `bun run dev` — `docker compose up -d`, then the API on `:8000` and the SPA on `:5173`. The pieces are also runnable alone: `bun run db:up`, `bun run api:dev`, `bun run curator:dev`. **A 502 on `/api` from the Vite dev server means the API is not up** (the proxy targets `localhost:8000`); the SPA itself still answers 200, which is what makes the symptom look like a front-end bug.
- API: `uv run uvicorn main:app --reload` (the root `main.py` re-exports the app).
- Curator UI (`apps/curator/`): `bun install` once at the repo root, then `bun run curator:dev` (`http://localhost:5173`, Vite proxies `/api` to `:8000`) or `bun run curator:build`. **Bun manages packages and scripts; Vite is the bundler** — do not replace it with `bun build` (ADR 0003). `bun run --cwd apps/curator typecheck|lint`.
- API contract: **generated and committed**. `bun run contract` dumps `packages/api-contract/openapi.json` and regenerates `apps/curator/src/api/schema.d.ts`; CI fails when either is stale. Never hand-write a request in the front — `src/api/client.ts` (openapi-fetch) is the only client, and ESLint bans the `fetch` global.
- Local infra: `docker compose up -d` (PostgreSQL 15 on 5432 + MinIO on 9000/9001). The database image is built from `docker/postgres/Dockerfile`: the pgvector base image plus PostGIS. The stock `postgis/postgis` images are still Debian 11 (bullseye), whose PGDG repository was retired, so pgvector cannot be installed there; starting from the pgvector image and adding PostGIS keeps both extensions available. PostGIS is installed but **not enabled by any migration** yet — the geospatial work is still ahead, and enabling it is a one-line migration.
- Workers: prefer the unified runner — `uv run python -m scrinalia.domains.archive.workers.runner <name> [--engine X --preset Y --batch N --option key=value --by "quem"]`, where names are `transfer`, `cleaning`, `ner`, `typology`, `thumbnail`, `conflict-judge`, `macro-category`, `quality-validator`, `embedding`. Pipeline order: `transfer -> cleaning -> ner -> typology -> thumbnail -> conflict-judge -> macro-category -> quality-validator -> embedding`. Each `worker_*.py` also has an `execute(db, ...)` + `__main__` block runnable directly. `--option` coerces `true`/`false` to booleans. Every run through the runner leaves a row in `archive_worker_runs` (see "Operations panel" below); the effective configuration follows `explicit argument > persisted override > signature default`, so a worker may run with a different preset than the one in its signature — `GET /api/v1/system/workers` is the way to see it.
- Database migrations: `uv run alembic upgrade head`; new revision: `uv run alembic revision --autogenerate -m "..."`; drift check: `uv run alembic check`.
- Tests live in `testing/` (renamed from `tests/`), not in the package. Run them from the
  root; `pythonpath` is **not** configured, because the app is imported as the installed
  package: `uv run pytest`; a single test:
  `uv run pytest testing/unit/archive/workers/test_worker_ner.py::test_name`.
- Lint/format: `uv run ruff check .` and `uv run ruff format .` (ruff is a dev dependency; line-length 120, double quotes). CI enforces `ruff format --check .`.
- `Procfile` defines the `api` process (`uvicorn` with `CUDA_VISIBLE_DEVICES=""`, i.e. CPU). The curator SPA has no process of its own: `create_app()` mounts `apps/curator/dist` at `/` when the build exists, which is why a deploy must build it (`bun run curator:build`).
- Type check: `uv run basedpyright` (scope and strictness in `[tool.basedpyright]`;
  it checks `src/scrinalia` and `main.py`).
- Pre-commit hooks (ruff lint/format + basedpyright): `uv run pre-commit install` once per clone; run manually with `uv run pre-commit run --all-files`.

## Language
- Everything in code is **English**: filenames, identifiers, comments, docstrings, log messages, Pydantic `Field` descriptions and internal errors.
- Portuguese is allowed **only for end-user-visible text**: curator UI strings (the React SPA), API response `message` values, and exception messages that the API forwards to users (`DomainException` subclasses).
- Never translate source-data literals that must match external payloads (e.g. the origin's field labels in `domains/ingestion/adapters/pmc_scraper.py`, declared as a `SourceSchema`) or LLM prompts written to reason about Portuguese text (e.g. `engines/LLMs/ollama_tag_entity_conflict.py`).
- `ValueError` is no longer translated to a client error: a global `ValueError` handler would turn programming mistakes into 400 responses. Use a `DomainException` subclass when the API must return a business status.

## Logging and configuration
- `src/scrinalia/core/config.py` exposes typed settings (`pydantic-settings`) as the module-level `settings`; `get_settings()` is `lru_cache`d and `get_settings.cache_clear()` resets it in tests. Env vars win over `.env`. `DB_PASS`/`S3_*` are `SecretStr` — unwrap with `.get_secret_value()`. `DATABASE_URL` is a property and percent-encodes the credentials.
- `src/scrinalia/core/logger.py` owns the loguru sinks (`LOG_DIR`/`LOG_LEVEL` from settings). `configure_logging()` is idempotent and only calls `logger.remove()` on first run, so importing it never tears down sinks another host already added. Third-party logs (uvicorn, Litestar) reach the sinks through `InterceptHandler`; `asgi.py` wires the same handler into Litestar's `LoggingConfig` because Litestar and uvicorn both apply a `dictConfig` at startup.
- `src/scrinalia/core/database.py` builds the engine lazily (`get_engine()`/`get_session_factory()`/`create_session()`), so importing it never needs a live database. `get_db()` yields a session and leaves the transaction to the caller; the API owns its transaction through `provide_unit_of_work` in `api/dependencies.py`.

## Observability
- **Two health endpoints, two questions, and they are not interchangeable.** `GET /health/live` and `GET /health/ready` (`api/controllers/health_controller.py`) are for an orchestrator: `live` touches nothing and answers 200 while the process answers, `ready` runs `SELECT 1` and answers 503 when the database does not. Both are **outside `/api/v1` and outside the contract** (`include_in_schema=False`), like Litestar's own `/schema`; an orchestrator must not have to know the API version. The human panel — `GET /api/v1/system/health` — is untouched and still answers *which piece is down*, paying for the Ollama and S3 calls that make that answer useful. Do not merge them: a liveness probe that consults the database restarts the API whenever the database restarts.
- **The readiness probe owns its engine** (`api/health_probe.py`): `NullPool` + `connect_timeout` + `statement_timeout`, created once. Without the timeouts a probe against an unreachable host hangs for the operating system's TCP timeout, which is minutes, and an orchestrator cannot tell that from a dead process. Widening the shared engine instead would change the behaviour of every request and every worker.
- **The root cause of a failure is a generated column, fed by one SQL function.** `archive_error_fingerprint(text)` is `IMMUTABLE`, and `error_fingerprint` is `GENERATED ALWAYS AS (public.archive_error_fingerprint(...)) STORED` in **both** `archive_worker_runs` and `archive_api_errors`. Never compute the fingerprint in Python: the generated column backfilled the existing rows with the very expression the new rows get, so there is exactly one definition and it cannot drift from the code that writes the message. The function is created by the `fe7fcab37207` migration and **mirrored in `testing/conftest.py`**, exactly like `immutable_unaccent` — the test schema is built by `create_all`, so the function must exist before it emits the generated columns. `public.` is part of the expression because that is how PostgreSQL reflects it back; without it `alembic check` reports drift that is not drift.
- **The error text carries the exception class** (`KeyError: 'nome'`), written by `WorkerRunRepository.finish` and `ApiErrorRepository.record`. `str(exc)` does not name the class, and the fingerprint reads that text: without it two different failures that share a sentence merge into one confident wrong root cause.
- **The API's own unexpected failures go to their own ledger**, written by `unhandled_exception_handler` through `ApiErrorRecorder` — its **own committed session**, never the request's (the request transaction is already rolled back, and bookkeeping must never turn one 500 into another). Only *unexpected* failures are recorded: a 404, a 409 and a 422 are answers the API owes a client, and recording them buries the real defects.
- **The catch-all handler is registered under the 500 status key, never under `Exception`.** Litestar resolves a handler by walking the exception's MRO and only falls back to the status key for exceptions that are **not** `HTTPException`. `Exception` is in the MRO of `NotFoundException`, so registering it by class turns every unknown route into a recorded 500 — measured, and pinned by `testing/integration/api/controller/test_unhandled_errors.py`.
- **Every request carries an id.** `RequestContextMiddleware` accepts `X-Request-ID` (sanitized: ≤64 chars, `[A-Za-z0-9._:-]`) or generates one, echoes it in the response header, publishes it in `scope["state"]` and binds it with `logger.contextualize`, so **every** record of that request carries it in `record.extra` of `ui_stream.jsonl` — including the one the 500 handler writes. The front reads it in `unwrap()` (`api/client.ts`) and `ErrorState` shows it as "referência". `contextvars` survive `sync_to_thread=True` handlers; that is verified, and it is what makes the id reach the code that actually fails. The **health probes are excluded from the access line** (`QUIET_PATHS`) but not from correlation: an orchestrator asks every few seconds and would rotate a 50 MB file with "200 OK".
- **`GET /api/v1/system/failures` groups both ledgers by the same fingerprint**, and the groups deliberately have no grand total: a worker execution and an HTTP request are different units, so a sum would be a number nobody can act on. `last_path`/`last_request_id` come from the latest **API** occurrence of the group, not from the latest occurrence of any kind — a mixed group whose newest row is a worker run still has a route worth showing.
- **Sentry is not used, on purpose.** The decision and its cost (no alerting, no paging) are in `docs/adr/0005-observability-without-an-external-service.md`. Do not add a hosted tracker without revisiting that ADR: the system is meant to be installed by another institution, offline.

## Database and infra
- Schema is owned by **Alembic** (`migrations/`, config in `alembic.ini`, connection URL from `core.config.settings`; `prepend_sys_path` is intentionally empty). Apply with `uv run alembic upgrade head`. The models in `src/scrinalia/domains/*/models/` are the single source of truth; `uv run alembic check` must report no drift.
- There is no `db-init` anymore. The schema **and** the extensions it needs are owned by Alembic: `pg_trgm` (fuzzy-search GIN indexes), `unaccent` (accent-insensitive full-text search) and `vector` (embeddings). Fresh volume -> `docker compose up -d` -> `uv run alembic upgrade head`. Recreate a clean volume with `docker compose down -v`.
- `testing/conftest.py` creates `pg_trgm`, `unaccent` + its `immutable_unaccent` wrapper and `vector` before `create_all` for the test database, because the test schema is built from the models and those columns/indexes depend on the extensions. Because the suite **drops the schema on teardown**, never run a server against the test database in parallel with pytest, and re-run `alembic upgrade head` before starting one again.
- The dev database is Alembic-managed. An older volume was found without `alembic_version` (schema created by `create_all`, drifting from the models in 43 places, which made every ORM read of a tag fail); it was rebuilt by copying the model tables into a database created with `alembic upgrade head` and renamed to `memoriacuritibana_legacy`. If a database ever drifts again, do **not** point pytest at it (the conftest drops the schema): build a clean database, copy the data and verify with `alembic check`.
- `.env` is gitignored. Keys in `src/scrinalia/core/config.py`: `DB_*`, `PUBLIC_SCRAPE_*`, `ACERVO_SOURCE`, `ACERVO_LANGUAGE`, `S3_*`, `OLLAMA_HOST_URL`, plus `LOG_DIR`/`LOG_LEVEL`/`DEBUG`. `docker-compose.yml` reads `DB_USER`/`DB_PASS`/`DB_NAME` (defaults admin/admin123/memoriacuritibana).
- Models are Postgres-specific (JSONB, ARRAY, native enums, GIN indexes) — they do not port to SQLite.

## Architecture conventions (easy to get wrong)
- DDD per domain: each domain has `models/`, `repository/`, `services/`, `schemas/`, `workers/`. Litestar controllers in `api/`; `api/dependencies.py` is the composition root: `provide_unit_of_work` owns the request transaction and each service provider receives it via `NamedDependency[UnitOfWork]`.
- Litestar handlers must annotate every parameter the framework resolves (`NamedDependency[...]`, `FromPath[...]`, `FromQuery[...]`) and pass an explicit `sync_to_thread` to routes and `Provide`. Inferred dependencies and parameters are deprecated and stop working in Litestar 3.0.
- Domain services receive repositories via constructor (`TagService(repo, document_repo)`); do not instantiate a session inside business logic.
- AI engines are pluggable via `registry.py` in each subpackage (`engines/classification`, `engines/NER`, `engines/clustering`, `engines/embeddings`, `engines/LLMs`): `get_engine(engine_name, preset, **kwargs)`, where `kwargs` overrides the preset. Contracts live in `engines/base.py` (Protocols). To add an engine, register it in `AVAILABLE_ENGINES` and add a preset. Heavy imports (torch, sentence-transformers) stay inside `__init__`, never at module level, so consulting a registry is cheap.
- Worker idempotency: each worker stamps a versioned key in a JSONB `execution_log` (`worker_ner_v2`, `worker_typology_classifier_v2`, `cleaning_rule_{id}`, `worker_macro_category_v1`, `worker_quality_validator_v1`, `worker_embedding_v1`), and the pending query filters by that key's absence (GIN indexes `ix_archive_exec_log` on documents, `ix_archive_tags_exec_log` on tags). Every new worker must follow this pattern + `flag_modified`. Document workers stamp `ArchiveDocument.execution_log`; `worker_macro_category` stamps `ArchiveTag.execution_log`, because its unit of work is the tag. `worker_embedding` stores the **MD5 of the embedded text** as the stamp value (not a status), computed by PostgreSQL, so a text change — including a human edit — puts the document back in the queue; `WorkerStamp.mark_value` writes it.
- Search: `DocumentSearchQuery.mode` selects `lexical` (default) or `semantic`. Lexical runs against the generated `search_vector` (`worker`-free, GIN, accent-insensitive via `immutable_unaccent`) plus tags/entities, with facets. The taxonomy match reads `domain_synonyms` too (`_merged_spelling_match`): canonicalising a spelling deletes the old row, and without that mapping a user typing the absorbed spelling loses the documents that were reachable only through it (measured after applying 40 plural merges: `lojas` lost 42 of its 54 documents, `homens` 30 of 35 — the full-text stemmer only covers documents whose *text* carries the word). Do not remove it when touching the taxonomy match, and keep it on both axes (tag and entity). Semantic runs against `ArchiveDocument.embedding` (`vector(384)`, HNSW cosine) and needs the term embedded, which `DocumentService` does through an injected embedder factory — the model is process-cached in `api/dependencies.py` and never loaded for a lexical request. `rank` is the `ts_rank`-based relevance for lexical and the cosine similarity for semantic. Do not reintroduce `semantic_search_vector`: it was a dead text column replaced by the generated `search_vector`.
- `DocumentRepository.upsert_archive_document` is **exclusive to the staging->archive migration**. The `ON CONFLICT` only updates if `staging_content_hash` changed and the status is not `HUMAN_APPROVED`. AI workers must NOT use it (they use surgical updates); otherwise the AI data is discarded.
- Governance: `ArchiveReviewStatus` controls the lifecycle (`HUMAN_APPROVED` blocks AI rewrites); tag x entity conflicts go to `archive_ai_review_queue`. **One documented exception:** `worker_embedding` deliberately does not use `ai_writable_documents()`, because the embedding is a derived index of the text rather than archival content — a `HUMAN_APPROVED` document whose text changed must be re-embedded or semantic search would serve a stale vector. It writes only the `embedding` column and its own stamp, and `REJECTED` documents are skipped.
- Governance is bidirectional, and the two directions are stored in different places on purpose. When a conflict resolves **in favour of the entity**, the tag name joins the tag-scoped `DomainStopwords`. When it resolves **in favour of the tag**, the term is recorded in `domain_ner_exclusions` (`DomainNerExclusion`) — a curation decision, not noise, carrying `reason`, `source` (`JUDGE`/`HUMAN`) and the `tag_id` that justifies it. Do not collapse the two: `TagRepository.get_stopwords()` reads only `TAG`/`ALL` scope deliberately, so an ENTITY-scoped ban cannot make the subject-axis purge delete the winning tag.
- The AI text composition lives in **SQL** (`domains/archive/repository/text_quality_repo.py`): PostgreSQL normalizes whitespace and subtracts the approved excerpts, and the same expression feeds the embedding text *and* its MD5 stamp, plus the text NER and typology read. Do not reintroduce a Python composition for the workers — `apply_excerpts_in_python` is the read-side mirror used only for the derived title, and an integration test pins the two together.
- `DomainTextTemplate.scope` says which consumer stops reading an excerpt: `EMBEDDING`, `NER` or `TITLE`. It exists because the measurement showed a title prefix helps the derived title and *hurts* the vector. A suggestion about `original_title` is born `TITLE`-scoped; do not widen a scope without re-running `testing/evaluation/retrieval_quality.py`.
- `ArchiveCleaningRule.rule_kind` separates `REWRITE` (the cleaning worker replaces the match) from `VALIDATE`/`LLM_CHECK` (the quality validator only flags). The cleaning worker filters `REWRITE` explicitly — without it a validation rule would rewrite the text. The LLM stage is opt-in: an engine is only built when an active `LLM_CHECK` rule exists.
- The staging -> archive CDC key is the **hash of the parsed record** (`StagingRecord.parsed_content_hash()`), not of the raw payload. A parser change leaves the payload byte-identical, so `run_staging_pipeline(force=True)` re-parses and the transfer then sees a real difference. Keep it that way or parser fixes will never reach the archive.
- Human curation: `PATCH /api/v1/documents/{id}` edits any ISAD(G) field, records the before/after of what changed in `archive_document_revisions` and sets `HUMAN_APPROVED`. The author comes from the session and is written as **two columns** (`changed_by` is the name the history prints, `changed_by_user_id` is the account); see "Authentication and authorization" below. `suggested_final_title` is derived on read from the `TITLE`-scoped excerpts and is never stored. `POST/DELETE /documents/{id}/tags[/{tag_id}]` and the entity pair do the same for one description's subjects (`link_tag`/`unlink_tag`/`link_entity`/`unlink_entity`): the revision stores the **whole list of names** on each side, not a diff of ids, and a repeated call writes no revision. `access_conditions` (ISAD(G) 4.1) and `is_published` are editable through the same command.
- **Diffusion is not review.** `is_published` is its own column, deliberately not `review_status = HUMAN_APPROVED`: review is a claim about the record, publication is a decision about what to expose. Reusing the status would make a typo fix equivalent to publishing **and** would lock every published document against AI rewriting through `ai_writable_documents()`. The public predicate is `is_published`, and since nothing is published by default the diffusion surface is born empty.
- The **public surface** (`api/controllers/public_controller.py`, `api/schemas/public.py`) reuses `DocumentService` and differs only in projection. Two rules: (1) `published_only` is set **server-side** and is not a client parameter, so no query string can ask for an unpublished record; an unpublished id answers 404, never 403, because a distinct status confirms the description exists. (2) `PublicDocumentSummary` is built field by field, never `model_validate` on the internal DTO — validating it would make every field the internal view gains automatically public. `NOT_PUBLIC_FIELDS` plus the published fields must remain an **exact partition** of `DocumentSummary`; a test fails if a new field is left unclassified, so the default for a new field is private.
- Facet counting has its own semantics and a test pins it: for each dimension the repository applies every filter **except that dimension's own**, so a selected rung still shows the others and the user can widen the search back. `published_only` is a filter and never excluded — no facet may lift the diffusion gate. The counts are computed from **the same clause the page came from** (fallback branch included), so the sidebar cannot disagree with the list. `DocumentListResponse.facets` is always present: a response that sometimes carries the sidebar and sometimes does not is a worse contract than one that always does.
- `GET /api/v1/curation/inbox` is the curator's work list. It is a **read view of existing predicates**; adding a queue is a line in `QUEUE_CATALOGUE` plus a count in `CurationRepository.count_pending()`, never a new route. The tag×entity collision count reads `archive_ai_review_queue` (indexed) and **not** the live trigram scan, which is the right thing for a home screen regardless of how fast the scan is.
- The arrangement plan catalogue separates the **decision** from the **run** exactly like the tag merges: `POST /hierarchy/plans/suggest` is idempotent by `code` and never rewrites a row that left `SUGGESTED`, so the same questions are not asked again. `GET /hierarchy/plans` carries `status_counts` for the **whole catalogue** (the screen's "34 de 52 decididos" cannot be derived from a page), and preview and apply share one planner so the approved number is the written number. Two traps, both shipped and both caught by looking at the screen: (1) `GET /hierarchy/flags` publishes the **union of four vocabularies** — `ProposalFlag`, `HierarchyIssue.NEAR_DUPLICATE_NODE`, `HierarchyViolation.LEVEL_NOT_ALLOWED_AS_CHILD` and `CodeFlag` — because that is what a plan row's `flags` actually carries; publishing only the first leaves the UI rendering raw codes, and `plan_flag_vocabulary()` exists so there is one definition to update. (2) `GET /hierarchy/diagnostics/summary` counts each issue with `limit=0` through the same code that serves each page, and deliberately has **no grand total**: the issues overlap (a Dossiê at the root is both an `ORPHAN` and a `DOSSIER_WITHOUT_PARENT`), so a sum would inflate the collection. `PATH_DIVERGENCE` is the one diagnostic whose evidence is a comparison, so it carries both `path` and `expected_path` in `detail`.
- **Trigram joins: `%` must be the only predicate.** A column-to-column `name % name` **does** use the GIN trigram index — PostgreSQL pushes the outer row down as a bitmap index key — so there is no need to materialise candidate pairs or to move the join into the application. What kills it is any extra condition OR-ed into the join: `name % name OR lower(name) = lower(name)` turns the join into a `Join Filter`, materialises the inner side and scans every pair. Measured on the real collection (6 142 tags x 3 808 entities): **52.9 s with the OR, 1.4 s without, identical results** — the `lower()` disjunct was redundant because `pg_trgm` normalises case (`similarity('Batel','batel') = 1`). Do not add prefilters in front of `%` either: an `abs(length(a) - length(b)) <= 3` "performance hack" used to sit in both `find_all_similar_pairs` and silently discarded **52-65%** of the real duplicate pairs, including `'alameda cabral'` vs `'al. alameda cabral'` (similarity 1.000, length difference 4). `testing/integration/archive/repository/test_trigram_joins.py` pins the assumption, the behaviour and the shape of both queries.
- `asgi.py` mounts `apps/curator/dist` at `/` through `api/spa.py` when the build exists, which is what keeps production same-origin and the project free of CORS. Two things to preserve: the static router must stay **registered after** the controllers (an `html_mode` catch-all would otherwise swallow `/api/v1` and `/schema`), and the client-side routing fallback lives in that router's `exception_handlers` — Litestar's `html_mode` serves `index.html` for a directory, not for a path the SPA owns, so without the fallback every deep link and every refresh answers 404.
- Tailwind v4 tokens are used with **parentheses**, not brackets: `bg-(--color-surface)`, `text-(--color-muted)`, `ring-(--color-line)`. The bracket form `bg-[--color-surface]` compiles to `background-color:--color-surface`, which is invalid CSS that the browser drops **silently** — the build stays green and the theme simply does not apply. This shipped once (105 occurrences) and was only caught by rendering the screens; when touching the UI, look at the page, do not trust a green `tsc`/`eslint`/`vite build`.
- The NER worker blocks terms by **token boundary**, not by exact name (`is_blocked_entity_name` in `worker_ner.py`). spaCy merges neighbouring tokens, so with `iptu` excluded the model still returns `"IPTU do Batel"` as a single entity and an exact comparison lets the false positive through. `get_ner_synonyms_rules()` also drops excluded spellings, otherwise the `EntityRuler` re-creates the term via `ent_id_`.
- Tag merges are one operation defined in **two halves**: `TagRepository.plan_merge()` (pure, describes the impact) and `apply_merge(plan)`. `TagService.merge` is plan + apply and `POST /tags/merge/preview` is the plan alone, pinned by a test that both produce the same numbers — do not compute the impact twice or the dry-run starts lying. Applying a merge must call `repoint_synonyms()` **before** `delete_tags()`: `domain_synonyms.canonical_tag_id` is `ON DELETE CASCADE`, so deleting first destroys the spellings absorbed by earlier merges and the next ingestion recreates the term. `create_synonyms` is an upsert for the same reason. The dedup curation cycle keeps the **decision** (`archive_tag_merge_proposals`) apart from the **write**: a human `APPROVED`/`REJECTED` verdict is a durable intent that the suggestion run never overwrites. The write is logged per absorbed tag in `archive_taxonomy_merge_log` *before* anything changes, and `undo_merge` restores from that snapshot — the row, the links, the classification and the spelling state. Two details that are easy to break: undo must delete **only** the links the merge created (`created_link_ids`; restoring the tag without that leaves the document with both spellings), and no `setval` is needed because the restored id came from the sequence in the first place. Entities carry the same two defects and the same fix (`EntityRepository.create_synonyms` upsert + `repoint_synonyms` before `delete_entities`), but entities have no proposal catalogue yet.
- **Applying a cluster settles the proposal.** `archive_tag_merge_proposals.status` goes `SUGGESTED -> APPROVED/REJECTED -> APPLIED`, and the batch writes `APPLIED` in the same savepoint that absorbs the tags: leaving it at `APPROVED` kept a finished batch in the approved queue forever, and clicking apply again answered "os membros já não existem" — a finished batch of 20 looked like 20 errors. `decided_by`/`decided_at` keep the *verdict*; the ledger keeps the *when*. Because `members` is a snapshot **without a foreign key**, the proposal outlives the tags it names, so the read computes `members_alive`, `canonical_alive` and `applicable` (canonical alive **and** more than one member alive) in one query per page — `applicable` is the single definition of "there is still work", used by the screen and by `merge_batch`, which reports those clusters in `skipped` and never in `failed`. The migration that added the state also backfilled it from the ledger, by fingerprint first and by absorbed name second (the merges made through `POST /tags/merge` carry no fingerprint); requiring a ledger entry is what keeps the backfill honest, since a stopword purge also leaves no member behind.
- **Stopwords have a scope, and the scope decides what is possible.** `domain_stopwords.word` is **unique**, so a term lives on exactly one axis: re-banning it *moves* it (`save_stopwords` is an upsert on `word`), because ignoring the second ban would leave the screen showing an axis the archivist just changed away from. `TagRepository.get_stopwords()` reads only `TAG`/`ALL` — a NER veto (`ENTITY`) must never make the subject purge delete a tag the curator kept, and there is a test for exactly that. Banning **deletes nothing**; `POST /tags/stopwords/purge` is the write, it **has no undo** (the merge keeps a ledger and restores; this deletes the row and the links cascade), and it is therefore gated behind `POST /tags/stopwords/purge/preview`, which lists the tags that would die. The purge route accepts an **empty body** so the screen applies the list it already showed, and still registers words when sent them, which is what makes "ban and purge in one call" possible. One naming trap: Litestar reserves the handler parameter name `scope` for the ASGI scope, so the route's query key is `axis` — a handler that used `scope` silently received the raw request, and only the route test caught it.
- **A route that answers a sentence answers a code too.** Every response carrying `message` inherits `RouteResponse` (`domains/archive/schemas/responses.py`), which pairs a `RouteMessageCode` with the Portuguese sentence. The code is the identity of the outcome — stable, English, keyed by a translation catalogue — and the sentence stays because a client that knows nothing about codes keeps working, and a code with no translation yet still has something to show. Three rules: the code describes the **outcome** and never the wording; adding one is an additive change to the enum, so an old client falls back to `message` instead of rendering an empty line; and **never** put a `Field(description=...)` on a `code` field, for the same shared-component reason as the enum bullet below. `testing/unit/api/test_route_message_codes.py` walks both schema packages and fails when a message-bearing response is left without a code — it walks the **submodules**, because a model lives in one and is only re-exported by `__init__`. The front reads every one of them through `routeMessage()` (`apps/curator/src/lib/messages.ts`), the single seam where a translation will land; the screens must not print `.message` directly.
- **A `Field(description=...)` on a field typed with a shared enum rewrites the enum's schema.** Litestar fetches the field's type from the schema registry and applies the field's kwargs to that **shared component** (`process_schema_result`), falling back to the type's docstring only when the description is still `None`. So the description does not document the field — it becomes the description of the enum for the whole document, and *which* field wins depends on the walk order, which depends on `PYTHONHASHSEED`. Measured: seeds 0 and 7 emitted a Portuguese field description for `StopwordsScope` while the others emitted the English docstring, so `bun run contract` produced two different files from identical code and CI's drift check failed at random. Document the **type** (its docstring reaches the contract and every referencing field inherits it) and never the field; `testing/unit/api/test_openapi_determinism.py` fails if a field of a contract component describes a shared type, and compares every enum component against its own docstring.
- The front talks to the API only through the generated client (`apps/curator/src/api/client.ts`, `openapi-fetch`); it never queries Postgres and never builds a URL by hand. Keep it that way — the API is the contract, and it is the one thing both surfaces (curator today, public site next) share.
- **Operations panel.** `/api/v1/system/*` and the `Sistema` section of the SPA. Four rules hold it together. (1) `workers/catalogue.py` is the **single definition** of a worker (order, axis, governance, stamp, counter path); it deliberately **imports no worker** — the target is resolved through `import_module` with a cache, because importing the nine modules at API start-up pulls spaCy/pandas/scikit-learn into a process that runs no worker (~1.7 s measured for spaCy alone). A new worker means a spec here, and a test fails if the catalogue, `runner.WORKERS` and `PIPELINE_ORDER` disagree. (2) Every worker exposes `count_pending(db, **options)` built from the **same** predicate `execute` uses (extract `pending_conditions(...)`), plus `count_processed`/`count_failed` only where the stamp is not enough (`thumbnail` reads `storage_thumbnail_uri`, `conflict-judge` has no cheap queue and carries `unmeasurable_reason` instead of inventing a number). The panel must never re-derive a predicate. (3) `describe_config` in each registry is the **read-only twin of `get_engine`**: it resolves preset + overrides and returns the dictionary without instantiating the engine, and a test captures the kwargs `get_engine` forwards to assert the two agree. `quality-validator` takes its engine/preset from the active `LLM_CHECK` rule (`engine_source="llm_check_rule"`) and the panel refuses to override it there — a second place to choose the same engine would be a second source of truth. (4) Configuration precedence is `explicit argument > archive_worker_settings row > signature default`; the row is partial on purpose (a `NULL` field keeps following the code), every write leaves a revision in `archive_worker_settings_revisions`, and `config` is refused as an option because it is a runner dataclass and not a JSON value.
- **The run ledger is written through its own committed session.** `archive_worker_runs` has one row per execution for **both** the CLI and the panel, carrying the resolved configuration, the duration and the outcome. `uq_worker_run_active` is a **partial unique index** on `(worker_name) WHERE status IN ('QUEUED','RUNNING')` — the concurrency guard is in the database, not in a process lock that `--reload` would drop. `WorkerRunLedger.enqueue` commits the `QUEUED` row **before** `WorkerRuntime.submit` hands the id to the thread; a row still inside the request's transaction would be invisible to the thread and the run would sit at `QUEUED` forever, so do not move this write into the request transaction. The API's executor runs **one worker at a time** (`WORKER_RUNTIME_MAX_WORKERS`) because the workers are CPU-bound, and it is not a scheduler: no retry, no cron. `api/lifespan.py` marks any `QUEUED`/`RUNNING` row it finds at start-up as `INTERRUPTED` (tolerating a database that is offline, because an operational convenience must not block boot) — that recovery assumes a **single API process**, so scaling to `uvicorn --workers > 1` requires moving the executor out.
- **Presets do not carry a host.** `OLLAMA_HOST_URL` reaches every preset-backed engine through `resolve_ollama_host()` (`core/config.py`); an explicit `--option host=...` still wins. Hardcoding the host in `PRESETS` made the environment variable a lie for every engine built through a preset — it only reached the generic `OllamaClient`. `GET /system/health` lists the models the presets require and which of them the server is missing, and never returns a secret value (only presence).
- **The three catalogues are closed vocabularies, and none of them deletes.** The level ladder (`/hierarchy/levels`), the subject drawers and the documental typologies (`/api/v1/typologies`, `archive_typologies`) are all tables instead of enums so the archivist can extend them without a deploy, and all three retire with `is_active=false` rather than deleting: the FK is `SET NULL`, so a removal would unclassify every description pointing at the row while erasing the record that it ever existed. The typology is a controller of its own and not a corner of the hierarchy or the taxonomy: it is the *diplomatic form* of the record (ata, ofício, planta), neither arrangement nor subject. Two rules hold it: (1) `get_active_typologies()` is the classifier's candidate labels, projecting **only** `(typology_id, name)` and filtering `is_active` — the bare name is the label, because appending `context_description` makes mDeBERTa lose the entailment as the label grows and collapse the collection onto one typology (measured), and the context column is documentation for the curator that must not even reach the worker's payload; (2) retiring is the only lever that reaches the model, so the catalogue screen keeps showing the weight of the retired ones. The human-path asymmetry is the ladder's: the staging load records an unknown level as unclassified and carries on, while an archivist choosing a typology is making a claim the catalogue has to answer, so `TypologyService.require` refuses an unknown id with 422 instead of storing `NULL`.
- **The language is code; the collection vocabulary is data.** `core/language/` holds one frozen `LanguageProfile` per language — stopwords, date grammar, street/placeholder/measure patterns, plural rules, the FTS dictionary, the spaCy model — and `ACERVO_LANGUAGE` selects it. The *rules* stay where they were (`staging/dates.py`, `domain/vocabulary.py`, `domain/normalization.py`) and read the profile instead of carrying its data, so a second language is a module and not a second parser. Everything the *collection* declares is a row: `archive_arrangement_vocabulary` (token, or whole code, to the name the proposal suggests — the whole code wins over the last token) and `archive_collection_terms` (typed by `CollectionTermKind`; a place kind claims the PLACE facet, `PERSON` goes nowhere), served by `/api/v1/vocabulary` and edited at `/vocabulario`. Three rules hold it: (1) the guard is **pure** and receives a `CollectionVocabulary`; an empty catalogue refuses nothing of its own and there is **no fallback to the reference collection**, or every other institution would silently be Curitiba; (2) `PT_BR.stopwords` is what the clustering engines discard and `domain_stopwords` is a curator's decision about the subject axis — **never collapse the two**, or a NER veto silences a tag the curator kept; (3) the FTS dictionary reaches the generated `search_vector`, so changing `ACERVO_LANGUAGE` is a **migration**, not a reboot, and `alembic check` reports the drift. The selectors and the Portuguese field names of a scraper stay **inside the adapter** — `SourceConfig` carries the origin, and an HTML layout is not configuration. See ADR 0008.
- **The origin's field vocabulary is a parameter, and the transform knows no site.** `SourceSchema` (`domains/ingestion/ports.py`) declares which of an origin's labels fills which staging column, the keys the adapter itself writes and which fields carry the date; the concrete one lives next to the adapter (`PMC_SOURCE_SCHEMA`), `ACERVO_SOURCE` selects it through `get_source_schema()`, and it reaches the transform as **Pydantic validation context** (`StagingDocumentDTO.model_validate(data, context={SOURCE_SCHEMA_CONTEXT_KEY: schema})`). Three rules: (1) the labels are the site's own and are **never translated** — they are payload keys, and translating one silently empties the column; (2) there is **no default origin**, because a fallback would make an installation that never declared its origin read the reference site's vocabulary (the ADR 0008 defect, one layer down) — `get_source_schema()` raises instead, and `run_staging_pipeline` fails fast; (3) the map's values are staging attributes, so a typo there files a column as unknown without failing — `testing/unit/ingestion/test_sources.py` checks every value against `StagingDocumentDTO.model_fields`.
- **"The origin wrote nothing" has one definition, in the language profile.** `PT_BR.false_null_values` owns the spellings; `empty_date_values` (the date set) and `placeholder_pattern` (the subject guard) are **declared views** of it, so a spelling added in one place is honoured everywhere. The subject view is deliberately a **subset**: the guard's verdicts are a measured behaviour (1.489 of the 8.155 real tags), and widening them would change which tags reach the classifier — a classification decision, not a cleanup. A `title` is never cleaned to `None`: it is required, and doing so dropped the whole document (measured). It falls back to `PT_BR.untitled_title` instead.
- **Pydantic at the boundary, `@dataclass` inside.** The split is a rule, not an accident of when a module was written: **Pydantic** is used where an object is *parsed* from something external (an HTTP body or query, a raw payload, a DB row) or *serialized into the contract* (the API response schemas) — validation and coercion are the point, and the ~200 models do exactly that. A **frozen dataclass** is used where the object is *computed internally* and only handed around: pure domain value objects (`SlicedReferenceCode`, `CollectionVocabulary`, `LanguageProfile`), private accumulators (`_Rung`, `_Plan`, `_NodeAccumulator`), runner config and origin declarations (`SourceConfig`, `SourceSchema`). Several sit on hot paths — `CollectionVocabulary.is_place` runs once per tag, `SlicedReferenceCode` once per reference code — and runtime validation there is paid for nothing. Do not "unify" them: converting a value object to Pydantic adds cost and a failure mode (a validation error where a type error belongs) without adding a boundary.
- **A write that changes a catalogue key must expire the relationship it was loaded with.** `DocumentRepository.update_review` assigns `level_id`/`typology_id` on a document fetched with `_eager_options()`, and builds the `DocumentSummary` from that same object a few lines later. The eager-loaded `level_ref`/`typology_ref` still point at the row the document was loaded with, so without `db.expire(doc, [...])` the response carries the **previous** name next to the new id — it shipped as `typology_id: 991` beside `typology: null`. Expire the attribute whenever its key is in `changes`; the derived name is the read contract and must never lag the foreign key it is derived from.
- **The tag x entity collision separates the decision, the write and the read — and the three used to be one thing.** `POST /taxonomy/conflicts/resolve/preview` returns **both** verdicts (`plan_conflict_resolution` is the single definition, so the dry run cannot promise another number), `archive_conflict_resolution_log` is the ledger with `DELETE /conflicts/resolutions/{id}` as its undo, and `GET /conflicts/judged` reads the judge's verdicts from `archive_ai_review_queue`. Three things are easy to get wrong. (1) **A resolved pair leaves the live scan** — the resolution deletes the losing row, so the trigram join cannot return it and the live list has nothing to annotate; the ledger and the queue are where the work survives. Measured: 84 of the judge's 88 decisions were auto-resolutions, i.e. invisible to the read that existed. (2) `ban_created` and `created_link_ids` are what make the undo exact: both writes are `ON CONFLICT DO NOTHING`, so reversing a later resolution must not lift a ban an earlier one planted, nor delete a link that predated it. (3) **`pair_kind` is the filter that makes the queue usable**: at 0,85 the live scan returns 5.408 pairs on the real collection, 5.050 of them the same spelling on both axes and 122 the same word written differently — a structural question and a spelling question, and mixed together neither is visible. The route's query key is `pair_kind` and **not** `scope`: Litestar reserves `scope` for the ASGI scope, and a handler parameter with that name silently receives the raw request (the stopwords route was bitten first and renamed its key to `axis`).
- **A facet over a mixed column buckets by code, and the public envelope is a partition.** `ArchiveDocument.anomaly_reasons` stores a stable code with an optional payload — `RULE_MATCH:<rule name>` and `LLM_SUSPECT:<free text the model wrote>` — so the raw value is not a dimension. `_anomaly_reason_key` is the one definition: the code, except `RULE_MATCH` which keeps the rule's name (a rule is a catalogue entry, and "which rule flagged this?" is the question) and `LLM_SUSPECT` which collapses to the code (a facet over prose is a long tail of buckets that never repeat). The facet groups by that expression and `anomaly_reason` filters by it, so the sidebar cannot offer a bucket the route refuses to filter. Two traps: `unnest` must live in a FROM clause — PostgreSQL rejects a `CASE` over a set-returning function in the select list ("argument of CASE/WHEN must not return a set") — and **`PublicDocumentListResponse` used to share `DocumentFacets` with the internal search**, so a new dimension published itself on the diffusion surface. `PublicDocumentFacets` is built field by field with `NOT_PUBLIC_FACETS` as an **exact partition**, mirroring `NOT_PUBLIC_FIELDS`: the default for a new dimension is private, and a test fails when one is left unclassified.
- **The "not a subject" suggestion is the deterministic guard, never a model.** `subject_exclusion_signal` answers *why* the guard refused a term where `is_subject_candidate` answers yes/no, reading the same predicates in the same order so the reason the worker skips a term is the reason the catalogue shows. The guard refuses **1.489 of the 8.155 real tags** (707 measures, 689 streets, 74 years, 16 person names, 3 placeholders) and nothing recorded it: `source='RULE'` sat in the table's check constraint with no writer, and `GET /tags/subject-exclusions/suggestions` plus the `source` field on the write are what make the distinction real. **Do not add a statistical or LLM proposal for the semantic half** (`pessoas`, `vista aérea`, `capanema`): the available signals lie — by document count the top of the orphans is `igrejas` (2.474, a real subject missing a drawer) and by low confidence it is `madeira` (0.30) and `ecletismo` (0.38), also real subjects — and a route that proposed them would be wrong with a confident tone, which is what the model already does. The candidate carries `is_place_term` because a street is refused by the subject axis **and** claimed by the PLACE facet: "not a subject" is not "goes nowhere".
- **Searches over what a person typed must escape the LIKE wildcards.** `escape_like()` + `LIKE_ESCAPE` (`domain/normalization.py`) exist so a `%` in a search box is a character and not "match everything": unescaped, the archivist gets the whole catalogue for a typo and the query stops using the trigram index. The collection search was never exposed to this because `domain/search.tokenize` (`[^\W_]+`) drops `%` and `_` before the SQL; what the new type-ahead routes pass is the **raw** term, so they build the pattern through the helper. The type-aheads (`GET /taxonomy/tags`, `GET /taxonomy/entities`) enforce a **two-character floor in the service**, not in the route, so every caller inherits the same one — one letter matches thousands of the 8.349 tags, and the box exists to *choose* a spelling, not to browse one. Two writes that look local are not: `PATCH /taxonomy/tags/{tag_id}` moves the drawer for **every** description carrying the tag (and the UI has to say so), and `POST /hierarchy/nodes/{id}/move` states where the node goes — `new_parent_id=null` means "to the root", so there is no way to change only the level and a screen must always send the parent it is showing. A curated tag is out of `worker_macro_category`'s reach because its queue predicate is `macro_category_id IS NULL`; the verdict is stamped in the tag's `execution_log` under `curated_macro_category`, since tags have no revision table.

## Authentication and authorization
- **Every operation of `/api/v1` declares how it may be reached**, with `opt={"access": Access.X}` on the route: `PUBLIC`, `AUTHENTICATED`, or one of the four permissions (`CURATE`, `CATALOGUE`, `OPERATE`, `ADMIN`). One guard registered on the application (`api/security.py`) enforces it, and `testing/unit/api/test_route_access.py` walks the built app and **fails when an operation is left unclassified**, when the open surface is not exactly the login plus the two diffusion routes, or when a writing `POST` escapes a write permission. A new route cannot ship unprotected by accident — only deliberately, in a diff.
- **The classification is per handler and cannot be per controller.** `resolve_guards` walks controller → handler and *extends*, so a route cannot relax what its controller declared; a guard on `TaxonomyController` would leak into the reads a `VIEWER` must reach. Do not "tidy" the classification into the controller.
- **The guard authenticates and authorizes; there is no authentication middleware.** A middleware runs outside Litestar's exception-handler layer, so its 401 is produced after `RequestContextMiddleware` has written the access line: the answer the front sees most often would be the one line with no status and no `X-Request-ID` echoed. A guard runs inside the route handler, before the body and before dependency resolution.
- **401/403 are `HTTPException`, never `DomainException`.** They are answers the API owes a client, and the unhandled-failure ledger records *defects*; a domain exception would also be mapped to a 400. A refused permission is **403 and not 404**: the 404-that-hides is the *public* surface's rule for unpublished records, not an administrative route's.
- **The author is never taken from the request.** `Author(name, user_id)` (`core/author.py`) is written by `author_columns`/`assign_author`, which are the only writers of the pair — a row with a name and somebody else's id is worse than one with no id at all. The text column is a **snapshot** (renaming somebody does not rewrite what they decided) and is never backfilled. The CLI's `--by` stays free text with `user_id=None`: it runs on the host, outside the HTTP threat model.
- **`AUTH_COOKIE_SECURE` is false by default on purpose** — the browser drops a `Secure` cookie over plain HTTP silently, so the login would look like it worked while nothing was stored. A deployment behind HTTPS sets it to true. The first administrator comes from `python -m scrinalia.domains.identity.cli create`, never from a route: a route that creates an admin when none exists is an open door whose only defence is a race on the first deploy.
- **The failed-login counter is not enforced yet, and cannot live in the request transaction**: a failed login raises and `provide_unit_of_work` rolls back, so the counter would be erased by the very failure it counts. It needs its own committed session, like `archive_worker_runs` (cycle B9.3).

## Tests
- Unit tests never load real models. The `mock_registry` fixture monkeypatches `AVAILABLE_ENGINES`/`PRESETS` to shield any registry; do not call Ollama/MinIO in tests.
- Integration tests require the Postgres test database: `docker compose -f docker-compose.test.yml up -d` (port 5433, tmpfs in RAM, `pgvector/pgvector:pg15` — the same image CI uses). `testing/conftest.py` defaults to `postgresql://test_user:test_password@localhost:5433/test_db`; override with the `TEST_DATABASE_URL` env var. The compose file publishes `${TEST_DB_PORT:-5433}`, because 5433 is a popular host port: when another project already holds it the container starts **without publishing anything** and the suite silently talks to the wrong PostgreSQL, which looks like a test failure rather than a port conflict.
- The test schema is built by `Base.metadata.create_all`, **not** by Alembic. So `alembic upgrade head` against the test database is a trap: `create_all` then skips the tables it finds, the suite runs against the migrated schema instead of the models, and the result is hundreds of failures that read as regressions (measured: 53 failed + 42 errors, all gone after the tables were dropped). If you migrate the test database to run a server against it, drop the schema before running pytest again.
- Key fixtures in `testing/conftest.py`: `db_session` (SAVEPOINT + rollback per test), `use_test_db` (patches `scrinalia.core.database.get_db`, opt-in), `generate_archive_doc`, `generate_typology`, `mock_ner_engine`, `mock_staging_doc`, and `reference_vocabulary` (sows the collection vocabulary the migration seeds, from the domain mirror). The last one exists because the test schema is built by `create_all`, which never runs a migration: a test that asserts the guard refuses `jaime lerner` has to declare that the collection carries the name, exactly like the migration does for the reference collection.
- Tests import the installed package (`scrinalia.*`), never a bare `core`/`domains`
  root, so the suite exercises the same boundary a consumer does. Because the source lives in
  `src/`, `uv sync` must have run at least once before pytest can import anything.
- CI (`.github/workflows/ci.yml`) has three jobs: a fast `uvx ruff` lint/format job; a test job that checks the committed `openapi.json` is current, then runs `alembic upgrade head` + `alembic check` and `uv run pytest` against a Postgres service on 5432; and a `frontend` job (Bun) that regenerates the TypeScript client and fails on drift, then type-checks, lints and builds `apps/curator`. Run the same checks locally before finishing.
