# auth

## Access, sessions and users

- **Every operation of `/api/v1` declares how it may be reached**, with `opt={"access": Access.X}` on the route: `PUBLIC`, `AUTHENTICATED`, or one of the four permissions (`CURATE`, `CATALOGUE`, `OPERATE`, `ADMIN`). One guard registered on the application (`api/security.py`) enforces it, and `testing/unit/api/test_route_access.py` walks the built app and **fails when an operation is left unclassified**, when the open surface is not exactly the login plus the two diffusion routes, or when a writing `POST` escapes a write permission. A new route cannot ship unprotected by accident — only deliberately, in a diff. The POSTs that only **compute** — the dry runs and previews, and `POST /taxonomy/tags/suggest-macro`, which runs the clustering and writes nothing — are pinned in `READ_ONLY_POSTS` and declare `AUTHENTICATED`, because the permission is about what a request can *change*. A writing route that lands in that set has to be added to it by hand; a compute-only route carrying a write permission is the asymmetry the set exists to make visible.
- **The classification is per handler and cannot be per controller.** `resolve_guards` walks controller → handler and *extends*, so a route cannot relax what its controller declared; a guard on `TaxonomyController` would leak into the reads a `VIEWER` must reach. Do not "tidy" the classification into the controller.
- **The guard authenticates and authorizes; there is no authentication middleware.** A middleware runs outside Litestar's exception-handler layer, so its 401 is produced after `RequestContextMiddleware` has written the access line: the answer the front sees most often would be the one line with no status and no `X-Request-ID` echoed. A guard runs inside the route handler, before the body and before dependency resolution.
- **401/403 are `HTTPException`, never `DomainException`.** They are answers the API owes a client, and the unhandled-failure ledger records *defects*; a domain exception would also be mapped to a 400. A refused permission is **403 and not 404**: the 404-that-hides is the *public* surface's rule for unpublished records, not an administrative route's.
- **The author is never taken from the request.** `Author(name, user_id)` (`core/author.py`) is written by `author_columns`/`assign_author`, which are the only writers of the pair — a row with a name and somebody else's id is worse than one with no id at all. The text column is a **snapshot** (renaming somebody does not rewrite what they decided) and is never backfilled. The CLI's `--by` stays free text with `user_id=None`: it runs on the host, outside the HTTP threat model.
- **`AUTH_COOKIE_SECURE` is false by default on purpose** — the browser drops a `Secure` cookie over plain HTTP silently, so the login would look like it worked while nothing was stored. A deployment behind HTTPS sets it to true. The first administrator comes from `python -m scrinalia.domains.identity.cli create`, never from a route: a route that creates an admin when none exists is an open door whose only defence is a race on the first deploy.
- **The lockout is written through its own committed session.** A failed login raises and `provide_unit_of_work` rolls back, so the counter cannot live in the request transaction — it would be erased by the very failure it counts. `LoginAttemptRecorder` (`domains/identity/repository/login_attempt_repo.py`) owns a session and commits, exactly like `archive_worker_runs`; `authenticate` records through it on failure and clears `failed_attempts`/`locked_until` **in the request transaction** on success (that asymmetry is deliberate: a success commits anyway). The backoff rides on the count — the *n*-th lockout doubles the window up to `AUTH_LOGIN_LOCKOUT_MAX_MINUTES` — so there is no second column. Only a **correct** password on a locked account is told the reason (`AccountLockedError`, 423); for anyone guessing the answer stays `InvalidCredentialsError`, so the lockout is not an enumeration oracle, and a wrong password while locked does **not** keep counting. Resetting the password lifts the lock.
- **The login rate limiter is a brake, not the guarantee.** `api/login_rate_limit.py` is a **process-local** sliding window per client address (429), in front of the per-account lockout; it resets on restart and does not follow the account, which is why the durable defence is the column. Do not build a lockout on it, and do not remove the per-account one because this exists.
- **`origin_guard` checks mutations and never reads, and a missing `Origin` is allowed.** Same-origin is the `Origin` authority equalling the request `Host` (default ports normalised), or the origin being in `AUTH_TRUSTED_ORIGINS` for a reverse proxy that rewrites `Host`. It is registered **before** `access_guard` so a cross-origin mutation is refused as cross-origin (403) and not as anonymous (401). The Vite dev proxy must keep `changeOrigin` **false** — rewriting Host to `localhost:8000` makes every dev mutation look cross-origin.
- **`is_locked` is computed on the server.** `AuthUserDTO.is_locked` derives from `locked_until` and the server clock; the browser must not compare timestamps during render (an impure `Date.now()` makes the component non-reproducible, and the front's lint rule rejects it). A lockout already served reads as `false` — the column keeps the past value until the next sign-in clears it.
- **`/api/v1/users` is the `ADMIN` surface, and the screen is a mirror that may only hide.** The accounts live in `api/controllers/users_controller.py`: create (the password is **temporary** — the administrator typed it, so `must_change_password=True`, exactly like the CLI's bootstrap), edit name/role/active, reset a password (which ends every session of the account), and list/revoke sessions. Two rules that are easy to undo: revoking a session id that belongs to **another account** answers 404 and not 200, because the id alone must not enumerate other people's sign-ins; and the last active administrator cannot be deactivated or demoted (`LastAdminError`, 409) — the one lockout with no way back through the UI. The SPA hides a menu entry by the area its screen *writes* (`lib/permissions.ts`, a mirror of `ROLE_PERMISSIONS`), while pure reads declare nothing and stay visible to every role: the mirror may hide and must never grant, and the 403 with a sentence remains the truth for a direct URL.
