# search

## The two modes

- Search: `DocumentSearchQuery.mode` selects `lexical` (default) or `semantic`. Lexical runs against the generated `search_vector` (`worker`-free, GIN, accent-insensitive via `immutable_unaccent`) plus tags/entities, with facets. The taxonomy match reads `domain_synonyms` too (`_merged_spelling_match`): canonicalising a spelling deletes the old row, and without that mapping a user typing the absorbed spelling loses the documents that were reachable only through it (measured: after a batch of plural merges the absorbed spellings had taken documents out of reach, and the full-text stemmer only covers documents whose *text* carries the word). Do not remove it when touching the taxonomy match, and keep it on both axes (tag and entity). Semantic runs against `ArchiveDocument.embedding` (`vector(384)`, HNSW cosine) and needs the term embedded, which `DocumentService` does through an injected embedder factory — the model is process-cached in `api/dependencies.py` and never loaded for a lexical request. `rank` is the `ts_rank`-based relevance for lexical and the cosine similarity for semantic. Do not reintroduce `semantic_search_vector`: it was a dead text column replaced by the generated `search_vector`.

## The public surface

- **Diffusion is not review.** `is_published` is its own column, deliberately not `review_status = HUMAN_APPROVED`: review is a claim about the record, publication is a decision about what to expose. Reusing the status would make a typo fix equivalent to publishing **and** would lock every published document against AI rewriting through `ai_writable_documents()`. The public predicate is `is_published`, and since nothing is published by default the diffusion surface is born empty.
- The **public surface** (`api/controllers/public_controller.py`, `api/schemas/public.py`) reuses `DocumentService` and differs only in projection. Two rules: (1) `published_only` is set **server-side** and is not a client parameter, so no query string can ask for an unpublished record; an unpublished id answers 404, never 403, because a distinct status confirms the description exists. (2) `PublicDocumentSummary` is built field by field, never `model_validate` on the internal DTO — validating it would make every field the internal view gains automatically public. `NOT_PUBLIC_FIELDS` plus the published fields must remain an **exact partition** of `DocumentSummary`; a test fails if a new field is left unclassified, so the default for a new field is private.

## Facets

- Facet counting has its own semantics and a test pins it: for each dimension the repository applies every filter **except that dimension's own**, so a selected rung still shows the others and the user can widen the search back. `published_only` is a filter and never excluded — no facet may lift the diffusion gate. The counts are computed from **the same clause the page came from** (fallback branch included), so the sidebar cannot disagree with the list. `DocumentListResponse.facets` is always present: a response that sometimes carries the sidebar and sometimes does not is a worse contract than one that always does.
- **A facet over a mixed column buckets by code, and the public envelope is a partition.** `ArchiveDocument.anomaly_reasons` stores a stable code with an optional payload — `RULE_MATCH:<rule name>` and `LLM_SUSPECT:<free text the model wrote>` — so the raw value is not a dimension. `_anomaly_reason_key` is the one definition: the code, except `RULE_MATCH` which keeps the rule's name (a rule is a catalogue entry, and "which rule flagged this?" is the question) and `LLM_SUSPECT` which collapses to the code (a facet over prose is a long tail of buckets that never repeat). The facet groups by that expression and `anomaly_reason` filters by it, so the sidebar cannot offer a bucket the route refuses to filter. Two traps: `unnest` must live in a FROM clause — PostgreSQL rejects a `CASE` over a set-returning function in the select list ("argument of CASE/WHEN must not return a set") — and **`PublicDocumentListResponse` used to share `DocumentFacets` with the internal search**, so a new dimension published itself on the diffusion surface. `PublicDocumentFacets` is built field by field with `NOT_PUBLIC_FACETS` as an **exact partition**, mirroring `NOT_PUBLIC_FIELDS`: the default for a new dimension is private, and a test fails when one is left unclassified.

## Matching and the trigram join

- **Trigram joins: `%` must be the only predicate.** A column-to-column `name % name` **does** use the GIN trigram index — PostgreSQL pushes the outer row down as a bitmap index key — so there is no need to materialise candidate pairs or to move the join into the application. What kills it is any extra condition OR-ed into the join: `name % name OR lower(name) = lower(name)` turns the join into a `Join Filter`, materialises the inner side and scans every pair. Measured on the reference collection: **52.9 s with the OR, 1.4 s without, identical results** — the `lower()` disjunct was redundant because `pg_trgm` normalises case (`similarity('Exemplo','exemplo') = 1`). Do not add prefilters in front of `%` either: an `abs(length(a) - length(b)) <= 3` "performance hack" used to sit in both `find_all_similar_pairs` and silently discarded **52-65%** of the real duplicate pairs, including `'exemplo longo'` vs `'ex. exemplo longo'` (similarity 1.000, length difference 4). `testing/integration/archive/repository/test_trigram_joins.py` pins the assumption, the behaviour and the shape of both queries.

## Wildcards and type-aheads

- **Searches over what a person typed must escape the LIKE wildcards.** `escape_like()` + `LIKE_ESCAPE` (`domain/normalization.py`) exist so a `%` in a search box is a character and not "match everything": unescaped, the archivist gets the whole catalogue for a typo and the query stops using the trigram index. The collection search was never exposed to this because `domain/search.tokenize` (`[^\W_]+`) drops `%` and `_` before the SQL; what the new type-ahead routes pass is the **raw** term, so they build the pattern through the helper. The type-aheads (`GET /taxonomy/tags`, `GET /taxonomy/entities`) enforce a **two-character floor in the service**, not in the route, so every caller inherits the same one — one letter matches thousands of tags, and the box exists to *choose* a spelling, not to browse one. Two writes that look local are not: `PATCH /taxonomy/tags/{tag_id}` moves the drawer for **every** description carrying the tag (and the UI has to say so), and `POST /hierarchy/nodes/{id}/move` states where the node goes — `new_parent_id=null` means "to the root", so there is no way to change only the level and a screen must always send the parent it is showing. A curated tag is out of `worker_macro_category`'s reach because its queue predicate is `macro_category_id IS NULL`; the verdict is stamped in the tag's `execution_log` under `curated_macro_category`, since tags have no revision table.
